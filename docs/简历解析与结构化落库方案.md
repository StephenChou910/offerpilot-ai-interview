# 简历解析与结构化落库方案

> 状态：初步确定，后续持续补充
>
> 更新时间：2026-09-29

## 一、简历解析方案

### 1. 当前问题

当前项目主要依赖文本层抽取：

- PDF 使用 PyMuPDF 提取文本；
- DOCX 使用 `python-docx` 读取段落；
- DOC 或其他格式尝试使用 Apache Tika；
- 未接入 PaddleOCR、Tesseract、EasyOCR 等 OCR 引擎。

因此，普通文本型 PDF 可以正常解析，但扫描件 PDF、图片型简历可能无法得到有效文本。

### 2. 确定的优化方向

采用“常规文本抽取优先 + 文本质量检测 + OCR 兜底 + 用户手动粘贴补救”的分层方案。

```text
上传文件
   ↓
文件类型校验
   ↓
常规文本抽取
   ↓
文本质量检测
   ├─ 合格 → 保存文本并进入简历分析
   └─ 不合格 → PDF 页面转图片 → OCR → 文本清洗 → 进入简历分析
```

### 3. 具体原则

1. 普通文本型 PDF、DOCX 等文件优先使用现有解析链路，避免不必要的 OCR 成本和延迟。
2. 当提取文本为空、文本过短或乱码比例过高时，自动触发 OCR 兜底。
3. OCR 引擎优先评估 PaddleOCR；也可以根据部署条件选择独立 OCR 服务。
4. 记录解析方式、解析状态、耗时、失败原因和 OCR 置信度等信息。
5. OCR 失败时允许用户直接粘贴简历文本，避免单个文件阻塞后续流程。

## 二、简历内容结构化落库方案

### 1. 总体原则

采用“核心字段关系型建模 + 原始 JSON 保留 + 证据定位”的方案。

项目、技能、实习/工作经历等内容进入独立结构化表，`profile_json` 继续作为 AI 原始输出、兼容和审计数据保留。

### 2. 数据层次

```text
简历文件 resumes
  └── 简历版本 resume_versions
        ├── 简历文本/解析信息
        ├── 个人信息 resume_profiles
        ├── 工作经历 resume_work_experiences
        ├── 项目经历 resume_projects
        │      └── 项目技术栈 resume_project_skills
        ├── 技能 resume_skills
        ├── 教育经历 resume_educations
        ├── 证书 resume_certifications
        └── AI 分析结果 resume_analyses
```

### 3. 第一阶段核心表

#### `resume_versions`

用于记录同一份简历的不同解析或修改版本：

- `resume_id`
- `version_no`
- `source_type`：`TEXT`、`OCR`、`MANUAL`
- `source_text`
- `parser_version`
- `ocr_used`
- `parse_status`
- `created_at`

#### `resume_profiles`

保存候选人基本信息：

- 姓名、电话、邮箱、所在地
- 目标岗位
- 工作年限
- 个人总结

敏感信息需要进行权限控制，必要时脱敏或加密。

#### `resume_work_experiences`

保存实习和工作经历：

- 公司名称
- 职位
- 经历类型：实习、全职、兼职等
- 开始时间、结束时间、是否在职
- 工作描述
- 工作职责
- 工作成果
- 排序号

#### `resume_projects`

保存项目经历：

- 项目名称
- 担任角色
- 起止时间
- 项目描述
- 个人职责
- 项目成果
- 遇到的问题
- 解决方案
- 排序号

项目字段重点围绕“职责、问题、方案、结果”设计，用于后续面试追问。

#### `resume_skills`

保存技能信息：

- 技能名称
- 技能类别
- 熟练程度
- 使用年限
- 最近使用时间
- 技能证据
- 排序号

#### `resume_project_skills`

建立项目和技能的关联：

- `project_id`
- `skill_id`
- `usage_description`

这样可以查询候选人在具体哪个项目中使用过某项技术。

### 4. 原始 JSON 的定位

暂不删除 `profile_json`，将其作为：

- AI 原始结构化输出
- 解析失败时的兜底数据
- 新字段灰度期间的兼容字段
- 重新解析时的审计记录

业务查询、岗位匹配、项目出题和面试生成逐步改为使用结构化表。

### 5. 证据与可追溯性

结构化字段后续应支持保存：

- `source_text_span`
- `source_page`
- `source_line`
- `confidence`
- `extraction_method`

用于定位字段来自原简历的具体页面或文本片段，支持人工校验、面试追问和数据审计。

### 6. 推荐实施顺序

第一阶段：

1. `resume_versions`
2. `resume_profiles`
3. `resume_work_experiences`
4. `resume_projects`
5. `resume_skills`
6. `resume_project_skills`

第二阶段：

- 教育经历
- 证书
- 语言能力
- 项目亮点明细
- 字段级来源、置信度和人工修正

## 三、后续待确定事项

- OCR 引擎采用本地 PaddleOCR 还是云服务；
- 简历版本与重新解析的具体规则；
- 结构化字段的数据库类型和 JSON 字段边界；
- AI 提取结果的校验与人工修正流程；
- 敏感个人信息的加密和访问权限；
- 解析、抽取和分析失败时的状态机设计。

## 四、出题、评分与训练闭环方案

### 1. 出题方案

采用“统一出题编排器”：

- 静态规则负责出题规划、题型比例、技能覆盖、难度范围、历史题目去重、格式校验和失败兜底；
- LLM 负责根据简历证据、岗位 JD、技能方向和历史表现生成主要面试题；
- 动态流程根据候选人的回答决定追问、难度变化、主题切换和面试结束；
- 完全不调用 LLM 的静态题目仅作为服务异常、离线模式或演示模式下的降级方案。

每道题应保存统一的题目上下文：

- `question_type`
- `target_skill`
- `target_project`
- `difficulty`
- `intent`
- `reference_answer`
- `key_points`
- `follow_up_goals`
- `evidence_required`
- 出题时引用的简历证据

### 2. 回答评分方案

评分器应基于题目上下文、参考答案、关键得分点、简历证据和用户回答进行结构化评估，不仅返回单一分数。

建议输出：

- 总分和各能力维度分；
- 命中的得分点和未覆盖的得分点；
- 事实性风险；
- 回答与简历证据的一致性；
- 回答的具体性、个人贡献、数据和结果完整度；
- 下一步追问建议；
- 评分置信度。

项目题需要特别区分技术回答质量和项目经历真实性，增加个人贡献真实性、项目细节一致性、方案合理性、指标可信度和抗追问能力等评价维度。

### 3. 面试评估方案

面试报告不只计算所有题目的平均分，而是汇总形成能力与风险画像，建议覆盖：

- 技术基础；
- 技术深度；
- 项目真实性；
- 项目 ownership；
- 问题分析能力；
- 系统设计能力；
- 表达和结构化能力；
- 岗位匹配度；
- 简历风险。

报告需要区分“明确答错”“未回答”“缺少评分依据”“评分置信度不足”和“简历证据与回答不一致”等不同情况。

### 4. 训练计划方案

训练计划从“低分题列表”升级为“能力缺口驱动”。例如，不仅记录某项技术得分低，还要说明候选人具体缺少概念理解、场景应用、方案取舍、指标验证或项目证据中的哪一部分。

训练任务可以包括：

- 概念补强；
- 项目复述；
- 技术方案讲解；
- 指标和结果补充；
- 追问抗压；
- 同题重答；
- 简历证据补全；
- 岗位专项训练。

每个训练任务应关联来源题目、来源项目或技能、触发的能力缺口、目标分数、推荐练习方式、验证标准、完成状态和重练后的提升幅度。

### 5. 统一职责划分

| 模块 | 主要职责 |
|---|---|
| 出题编排器 | 决定考察主题、项目、技能和能力目标 |
| LLM 出题器 | 生成具体题目、参考答案和评分点 |
| 评分器 | 根据评分点、简历证据和回答进行评估 |
| 面试评估器 | 汇总能力、风险和岗位匹配情况 |
| 训练计划器 | 将能力缺口转成可执行训练任务 |
| 规则引擎 | 去重、边界校验、降级、状态和进度控制 |

## 五、Agent/编排框架选型方案

### 1. 当前判断

项目已经使用 LangChain 的部分基础能力，例如 `ChatOpenAI`、Prompt 模板和结构化输出，但目前没有使用 LangGraph，也没有形成完整的 Agent 图或工具调用循环。

### 2. 确定的架构方向

采用“自定义业务编排为主、LangChain 负责 LLM 基础能力、LangGraph 局部用于多轮动态追问”的混合架构。

不把整个系统改造成全局 Agent，不让 LLM 直接控制核心业务状态、评分边界和数据持久化。

```text
业务层：自定义 Interview Orchestrator
        ↓
状态层：明确的 Interview State / Topic State
        ↓
LLM 层：LangChain ChatModel + Structured Output
        ↓
工具层：题库、简历、评分、知识库、历史训练记录
```

### 3. 自定义编排部分

以下流程继续由业务代码和显式状态机控制：

- 面试 session、topic、题目和轮次状态；
- 是否追问、切换主题或结束面试；
- 评分结果持久化和事务边界；
- 简历解析、OCR、数据库写入和 Redis 异步任务；
- 分数校准、训练任务状态和失败重试。

### 4. LangGraph 的适用范围

后续可以局部引入 LangGraph，用于动态面试中单个 topic 的多轮教练流程：

```text
读取当前 topic
   ↓
理解用户回答
   ↓
识别能力缺口
   ↓
选择追问策略
   ↓
生成追问
   ↓
判断继续、切换或结束
```

LangGraph 主要用于显式状态、条件分支、中断恢复和多轮上下文管理；最终 session 状态、数据库写入和训练计划生成仍由业务服务控制。

### 5. 暂不采用的方式

- 不全面改造成 LangChain Agent；
- 不让 LLM 自由选择数据库操作；
- 不让 Agent 直接决定分数和训练计划；
- 不用 Agent 替代现有状态机和异步任务系统。

## 六、知识库与知识图谱升级方案

### 1. 当前问题

当前项目已经具备知识库上传、文本切分、Embedding、向量检索、RAG 对话和知识图谱三元组抽取能力，但知识库与面试业务基本独立：

- 普通出题流程没有使用知识库检索结果；
- 知识图谱没有参与题目规划、追问、评分或训练计划；
- 图谱主要是实体和三元组的简单存储，缺少统一本体、关系词表、实体消歧和完整证据链；
- 知识库检索还需要补充更完整的文档元数据和混合检索能力。

### 2. 总体方向

建立统一的“面试知识增强层”：

```text
简历画像 + 岗位 JD + 历史表现
              ↓
       面试目标与能力缺口
              ↓
   向量检索 + 关键词检索 + 图谱检索
              ↓
        证据融合与重排
              ↓
      出题 / 追问 / 评分 / 训练
```

知识库负责文档证据和语义检索，知识图谱负责实体关系和路径推理，二者通过混合检索、重排和证据融合共同服务面试链路。

### 3. 知识库升级

文档处理链路升级为：

```text
文件 → 文档解析/OCR → 版面和章节识别 → 语义切分 → 元数据补充 → Embedding + 倒排索引
```

每个 chunk 后续应支持保存：

- 文档 ID和知识库 ID；
- 标题和章节路径；
- 页码和原文位置；
- 文档类型、版本和更新时间；
- 技能标签、岗位标签、难度；
- 知识类型；
- 来源和解析方式。

检索采用混合检索：

```text
BM25 / 关键词检索 + 向量检索 + 知识图谱检索
                         ↓
                    RRF 或加权融合
                         ↓
                    Cross-Encoder 重排
```

知识内容建议分类为概念定义、原理解释、框架用法、工程实践、设计模式、故障案例、性能优化、面试题、反例边界和行业规范。

### 4. 知识图谱升级

先建立面试领域本体和标准关系词表。

建议实体类型包括：

- `Technology`
- `Framework`
- `Language`
- `Database`
- `Middleware`
- `Concept`
- `Pattern`
- `Scenario`
- `Failure`
- `Metric`
- `JobRole`
- `Skill`
- `Project`
- `Candidate`

建议关系类型包括：

- `USES`
- `DEPENDS_ON`
- `ALTERNATIVE_TO`
- `SOLVES`
- `CAUSES`
- `OPTIMIZES`
- `REQUIRES`
- `PART_OF`
- `APPLIES_TO`
- `MEASURED_BY`
- `MENTIONED_IN`
- `SUPPORTED_BY`

每条关系后续应保存来源文档、来源 chunk、原文证据、抽取模型、置信度、审核状态、生效时间和版本号。

### 5. 接入面试链路

出题前增加知识增强检索节点：

```text
简历项目/技能 + 岗位 JD + 当前能力目标
                     ↓
                 构造检索查询
                     ↓
             混合检索知识库和图谱
                     ↓
                   证据重排
                     ↓
                 生成题目上下文
                     ↓
                 LLM 生成题目
```

检索结果应参与：

- 题目生成和参考答案；
- 动态追问和边界问题；
- 回答评分和事实校验；
- 能力缺口识别；
- 个性化训练计划。

所有 LLM 生成的题目和结论尽量绑定知识来源，支持追溯和校验。

### 6. 知识库与图谱存储选型

#### 当前阶段

暂不立即引入 Neo4j 等专业图数据库，继续使用 PostgreSQL 作为统一数据底座：

```text
PostgreSQL
├── 结构化业务数据
├── 知识文档和 chunk
├── pgvector 向量
└── 知识图谱实体与关系表
```

保留并完善现有实体表和三元组表，增加本体、来源证据、置信度、审核状态、版本和索引。

原因是当前图谱主要是实体查询和一到两跳关系查询，且与简历、面试和训练数据关联紧密。继续使用 PostgreSQL 可以降低运维、事务和数据同步复杂度。

#### 图算法

近期可以使用 `NetworkX` 或 `igraph` 做轻量、离线图算法，例如路径查询、关联度、中心性和技术关系分析；普通一跳、两跳查询继续使用 PostgreSQL。

#### Neo4j 的引入条件

当出现以下情况时再评估 Neo4j 或其他专业图数据库：

- 图谱达到百万级以上实体或关系；
- 频繁进行三跳以上路径查询；
- 需要复杂路径匹配、最短路径或社区发现；
- 图谱成为独立产品，需要专业图谱分析和可视化；
- PostgreSQL 图查询性能无法满足面试实时要求。

#### 演进路线

```text
阶段 1：PostgreSQL + pgvector + 关系型图表
        ↓
阶段 2：PostgreSQL 图表 + NetworkX/igraph 离线算法
        ↓
阶段 3：评估 Neo4j 或其他图数据库
        ↓
阶段 4：必要时采用 PostgreSQL + Neo4j 双存储
```

如果未来采用双存储，PostgreSQL 作为业务事实源，Neo4j 作为图查询和算法投影，通过异步任务同步，不让 Neo4j 成为唯一数据源。

## 七、Agent 任务编排升级方案

### 1. 当前编排位置

当前项目已经存在 Agent 编排雏形，但主要服务于智能下载和知识构建任务，尚未成为简历、面试、知识库和训练模块统一使用的工作流平台。

主要编排链路为：

```text
SmartDecisionTree
        ↓
PlanningAgent
        ↓
ExecutionAgent
        ↓
QualityAgent
        ↓
SummaryAgent
```

此外，项目还使用 Redis Stream 编排简历分析、知识库索引和面试评估等后台任务；动态面试则有独立的 session/topic/turn 业务状态机。

### 2. 当前能力评估

#### 超时

目前只有 HTTP 客户端、搜索服务和部分底层调用的局部超时控制，没有统一的任务超时、步骤超时、工作流 deadline、取消传播、超时降级和超时状态持久化机制。

#### 质量门禁

`QualityAgent` 已有两阶段质量检查：规则检查下载结果，必要时调用 LLM 评估覆盖度和多样性，并支持失败任务选择性重试。但该能力主要针对知识下载任务，尚未抽象为适用于简历、出题、评分和训练计划的通用质量门禁。

#### 成本统计

项目已有 `CostController`、Token 使用统计、模型价格表、预算限制，以及执行、成本和性能数据库模型。但目前不同模块的 LLM 调用尚未全部统一接入，内存统计与数据库持久化、流式调用、失败调用和重试调用的成本归因也需要进一步统一。

#### 文档与实现一致性

Agent 编排 README 中提到的部分 `agent_chain.py`、`nodes/` 等实现与当前目录并不完全一致，需要后续同步文档和代码边界。

### 3. 总体架构方向

采用“三层编排”架构：

```text
第一层：业务工作流编排
        负责简历、知识库、面试和训练流程

第二层：Agent/LLM 子流程编排
        负责规划、检索、生成、评分、质检和总结

第三层：基础任务执行层
        负责 Redis Stream、重试、超时、取消、死信和持久化
```

### 4. 第一层：业务工作流

继续由自定义服务和显式状态机控制：

- 简历解析和 OCR；
- 知识库索引和知识图谱抽取；
- 面试 session、topic 和 turn；
- 面试评估和报告生成；
- 训练计划和训练任务状态；
- 数据库事务与业务数据持久化。

### 5. 第二层：LLM 子流程

- 继续使用 LangChain ChatModel 和结构化输出；
- 后续可局部使用 LangGraph 管理动态面试追问、复杂检索和质量修正等多轮 LLM 子流程；
- 通过统一 LLM Gateway 采集模型、Token、成本、耗时、重试和错误信息；
- 不让 LLM 直接控制核心业务状态、数据库事务和评分边界。

### 6. 第三层：任务基础设施

基于现有 Redis Stream，统一补充以下字段和能力：

- `workflow_id`
- `task_id`
- `step_id`
- `parent_task_id`
- `deadline`
- `retry_policy`
- `idempotency_key`
- `cancellation`
- `dead_letter`
- `heartbeat`
- `checkpoint`
- execution event

任务状态需要支持等待、运行、成功、部分成功、失败、超时、取消和重试中等状态，并能够恢复和审计。

### 7. 是否引入新的编排框架

当前不全面引入新的 Agent 或工作流框架。现阶段优先统一现有自定义编排和 Redis Stream 的抽象，补齐工作流状态、超时、取消、重试、质量门禁、成本统计和执行追踪。

LangGraph 只在需要显式状态、多轮上下文、中断恢复和条件分支的 LLM 子流程中局部使用，不作为全局任务调度器。

当工作流持续时间、跨服务恢复、定时任务、补偿事务和 checkpoint 需求显著增加，且 Redis Stream 自维护成本过高时，再评估 Temporal、Celery、Prefect 等专业工作流框架。

### 8. 优先建设顺序

1. 统一任务和步骤状态模型；
2. 统一超时、取消和重试策略；
3. 统一质量门禁和失败降级；
4. 统一 LLM Token、成本、耗时和错误追踪；
5. 增加 workflow/task/step 级执行日志和可观测性；
6. 再根据实际规模评估是否引入专业工作流框架。

## 八、其他待优化问题的补充方案

本节只记录前文尚未形成明确方案的问题，避免重复简历解析、知识增强、出题评分、任务编排和框架选型章节中的内容。

### 1. 安全配置与生产环境治理

#### 问题

当前配置中仍存在开发环境默认值，例如数据库密码、对象存储凭据、本地服务地址和无密码 Redis。开发环境可以保留默认值，但生产环境不能依赖这些默认配置启动。

#### 方案

1. 将数据库、Redis、MinIO、JWT、LLM 和第三方服务密钥全部改为必填环境变量或密钥管理服务。
2. 生产模式下禁止使用默认密码、默认 access key 和空 JWT secret。
3. 启动阶段执行配置检查：密钥缺失、默认凭据、弱密码和不安全外部地址直接阻止启动。
4. 区分 `development`、`test`、`staging` 和 `production` 配置，避免测试配置进入生产。
5. 对配置中的密钥和连接串进行日志脱敏，禁止打印完整 token、密码和 Authorization header。
6. 为数据库、Redis 和对象存储设置最小权限账号，并限制网络访问范围。

### 2. 文件上传与隐私数据安全

#### 问题

简历和知识库文档包含个人信息和业务资料，仅进行扩展名、MIME 或大小校验还不够；文件还可能包含恶意内容，且原始文件和解析文本都属于敏感数据。

#### 方案

1. 对扩展名、声明 MIME、文件魔术字节和实际文件结构进行多重校验。
2. 对压缩包、嵌套文档和异常 PDF 做深度检查，限制解压层级、页数、对象数量和资源大小。
3. 增加病毒扫描或隔离扫描流程；扫描完成前不允许进入解析和索引流程。
4. 文件解析放在受限进程或独立 worker 中，限制 CPU、内存、执行时间和网络权限。
5. 对对象存储使用私有 bucket 和短时签名 URL，不直接暴露永久公开地址。
6. 增加文件和文本的删除、导出、脱敏和保留期限策略；删除简历时同步清理对象存储、解析版本、向量、图谱证据和相关缓存。
7. 将姓名、电话、邮箱等个人信息纳入敏感字段治理；发送给外部 LLM 前支持脱敏或按用户授权决定是否发送。

### 3. 统一可观测性方案

#### 问题

当前日志和耗时、Token、成本、检索命中、质量结果分散在各模块，难以追踪一次请求完整经过了哪些步骤。

#### 方案

建立统一请求和执行链路标识：

```text
request_id
  └── workflow_id
        └── task_id
              └── step_id
                    └── llm_trace_id
```

所有 API、Redis 任务、LLM 调用、检索和数据库写入都带上这些标识，并统一记录：

- 用户和租户；
- 功能类型；
- 开始时间、结束时间和耗时；
- 当前状态；
- 模型、供应商和版本；
- Prompt/Completion/Total Token；
- 成本估算；
- 检索命中文档和图谱证据；
- 重试次数；
- 质量分数；
- 错误类型和降级路径。

日志分为结构化业务日志、指标和链路追踪三类。第一阶段可以先统一 JSON 日志和数据库执行记录，后续再接入 OpenTelemetry、Prometheus 和 Grafana。

### 4. 测试与离线评测方案

#### 问题

当前已有单元测试和部分 RAG/质量基线，但 OCR、知识增强出题、任务重复消费、成本统计和多用户隔离仍缺少完整验证。

#### 方案

建立四层测试体系：

1. **单元测试**：覆盖解析器、切分器、检索融合、评分规则、状态转换和成本计算。
2. **契约测试**：验证前后端 DTO、枚举、错误码和 OpenAPI 结构一致。
3. **集成测试**：使用临时 PostgreSQL、Redis、对象存储和模拟 LLM，验证完整任务链路。
4. **端到端测试**：从注册、上传简历、生成面试、提交回答到报告和训练计划进行完整验证。

重点补充以下测试数据和场景：

- 文本型 PDF、扫描型 PDF、图片简历和乱码文件；
- OCR 失败、LLM 超时、结构化输出错误和重试；
- Redis 消息重复投递、worker 重启、pending 认领和死信；
- 知识库检索到出题、评分和训练的完整链路；
- 多用户访问、删除级联和越权访问；
- Token、成本、流式调用和重试调用的统计准确性。

同时保留离线评测集，对 RAG 召回、题目相关性、评分一致性、事实准确性和训练任务有效性进行版本化比较。

### 5. 前后端契约治理

#### 问题

难度、面试模式、任务状态、分析状态和题目类型等字段部分仍以自由字符串传递，容易出现前后端静默回退或含义不一致。

#### 方案

1. 后端为跨模块状态和类型定义统一枚举。
2. 请求入口严格校验枚举值、长度、范围和组合关系。
3. 通过 OpenAPI 生成或校验前端 TypeScript 类型，减少手工重复定义。
4. 为每次 API 变更维护契约版本和兼容策略。
5. 错误响应统一使用错误码、用户提示、可重试标记和 trace ID。
6. 对关键接口增加契约测试，确保前端实际请求和后端 schema 一致。

### 6. 外部工具与占位功能治理

#### 问题

部分 GitHub、arXiv、MCP 和 Agent 工具仍是占位或简化实现，文档中容易被误认为已经具备完整能力。

#### 方案

为每个外部工具建立能力清单和生命周期状态：

- `AVAILABLE`：已实现并有测试；
- `EXPERIMENTAL`：可用但不保证稳定；
- `PLACEHOLDER`：仅有接口或模拟结果；
- `DISABLED`：生产环境禁用。

接口返回中标记能力状态，前端不展示不可用功能。占位实现不得返回看似真实的业务内容，应明确返回未实现错误或模拟标记。每个外部服务需要配置超时、重试、限流、熔断、凭据轮换和失败降级策略。

### 7. 多用户与数据隔离治理

#### 问题

项目多数业务表已经带有 `user_id` 或通过用户依赖进行过滤，但知识图谱、部分任务记录、缓存键和对象存储路径仍需要系统性检查，避免出现跨用户数据泄露。

#### 方案

1. 所有用户数据查询默认强制带用户或租户范围，禁止依赖调用方自行拼接过滤条件。
2. 对简历、知识库、面试会话、图谱、任务和训练记录建立统一 ownership 检查。
3. Redis key、对象存储 key 和异步消息携带用户/租户范围。
4. 管理员查询和普通用户查询使用不同权限依赖。
5. 增加越权访问、猜 ID、跨用户检索和删除级联测试。
6. 后续如支持组织或企业场景，将 `tenant_id` 作为一级隔离字段，而不是只依赖 `user_id`。

### 8. 方案落地顺序

1. 先完成生产配置校验、文件安全和多用户隔离；
2. 再统一 API 契约、错误模型和执行链路标识；
3. 建立集成测试、E2E 测试和离线评测基线；
4. 接入统一日志、指标、链路和成本观测；
5. 最后治理外部工具状态，并根据真实运行数据决定是否引入更重的基础设施。

## 九、详细实施路线图

### 实施原则

1. 每个阶段都应可独立上线，避免长时间大规模重构。
2. 数据库变更先加表/加字段，再双写和回填，确认稳定后才切换读路径。
3. 所有涉及 LLM 的新能力都需要降级路径、成本上限和离线评测集。
4. 每阶段结束必须包含迁移脚本、自动化测试、监控指标和回滚说明。
5. 未通过验收标准的阶段不进入下一阶段。

### 阶段 0：基线盘点与安全加固

#### 目标

让现有系统在不改变主要业务行为的前提下具备可观测、可回滚、可安全运行的基础。

#### 实施步骤

1. 整理当前 API、数据库表、Redis Stream、对象存储 bucket、LLM 调用点和外部工具清单。
2. 标记全部占位功能、实验功能和生产功能，前端隐藏或明确标识不可用能力。
3. 增加环境分类：`development`、`test`、`staging`、`production`。
4. 生产环境启动时校验 JWT secret、数据库密码、Redis 密码、对象存储凭据和 LLM API Key；发现默认值或缺失值时拒绝启动。
5. 对日志中的 Token、密码、Authorization、电话和邮箱进行脱敏。
6. 为 API 请求生成 `request_id`，并在日志、错误响应和异步消息中透传。
7. 对简历、知识库、面试和任务接口完成一次用户归属与越权访问审计。
8. 建立开发、测试和预发布环境的最小部署文档与备份方案。

#### 交付物

- 配置检查器和生产启动校验；
- 外部工具能力清单；
- 结构化日志基础规范；
- 用户数据权限审计清单；
- 基础 smoke test。

#### 验收标准

- 生产配置缺失、默认凭据或弱密钥时服务不能启动；
- 任意 API 错误可返回 trace/request ID；
- 普通用户无法读取、修改或删除其他用户的简历、知识库和面试数据；
- 日志中不出现完整密码、Token 和个人联系方式。

### 阶段 1：统一任务基础设施与 LLM Gateway

#### 目标

统一后台任务、LLM 调用、超时、重试、成本和执行追踪，不改变现有面试产品流程。

#### 实施步骤

1. 为 Redis Stream 消息增加 `workflow_id`、`task_id`、`step_id`、`user_id`、`idempotency_key`、`created_at` 和 `deadline`。
2. 扩展任务状态：`PENDING`、`PROCESSING`、`RETRYING`、`COMPLETED`、`PARTIAL`、`FAILED`、`TIMEOUT`、`CANCELLED`、`DEAD_LETTER`。
3. 将重试次数、最后错误、下一次重试时间和死信原因持久化，不只保存在 worker 内存。
4. 为任务添加统一的超时策略：步骤超时、任务总超时、重试退避、最大重试次数和取消传播。
5. 建立 LLM Gateway，所有 `ChatOpenAI`、流式调用和 Embedding 调用统一经过该层。
6. Gateway 在调用前执行预算检查和上下文长度控制，调用后记录模型、供应商、Token、成本、耗时、错误和重试次数。
7. 先让简历分析、知识库索引、静态出题、动态评分四条核心链路接入新 Gateway。
8. 提供任务查询、重试、取消和死信重放的管理接口；普通用户只能查看自己的任务。

#### 数据与接口改动

- 新增或扩展 workflow/task/step 执行表；
- 为现有异步消息添加版本化 payload；
- 为 LLM 调用增加统一 trace metadata；
- 增加任务状态查询和安全重试接口。

#### 验收标准

- worker 重启、消息重复投递时不会重复写入关键业务结果；
- 超时任务可被标记、查询、重试或进入死信；
- 任意一次 LLM 调用都能定位到业务请求、任务、模型、耗时、Token 和成本；
- 单个用户、单次会话和单个功能的成本可以统计。

### 阶段 2：简历解析与结构化数据底座

#### 目标

实现文本抽取优先、OCR 兜底，并将简历核心内容从 `profile_json` 逐步迁移至关系型结构化数据。

#### 实施步骤

1. 设计并创建 `resume_versions`、`resume_profiles`、`resume_work_experiences`、`resume_projects`、`resume_skills` 和 `resume_project_skills` 表。
2. 所有新表都包含版本归属、排序、来源文本、页码/文本位置、抽取方式、置信度、创建时间和更新时间。
3. 保留现有 `resumes.resume_text` 和 `resume_analyses.profile_json`，将其定位为原始文本和 AI 原始输出。
4. 在文档解析后增加文本质量检测：空文本、长度过短、乱码比例、有效字符比例和页级文本覆盖率。
5. 仅在质量检测不通过时触发 OCR；OCR 结果与常规抽取结果分别记录来源和置信度。
6. 选择并验证 OCR 引擎，优先评估 PaddleOCR 的中文识别和部署成本；为云 OCR 保留适配接口。
7. AI 结构化抽取输出改为版本级 schema，同时对项目、技能、工作经历进行字段级校验。
8. 先双写 `profile_json` 和结构化表；对历史简历增加后台回填任务。
9. 前端详情页先增加结构化内容展示和人工纠正入口，但不删除原始文本视图。
10. 完成回填和质量抽样后，面试、诊断和项目打磨逐步切换为优先读取结构化表。

#### 验收标准

- 文本型 PDF、DOCX、扫描型 PDF 都能进入可解释的解析状态；
- OCR 只在必要时调用，且结果可追溯；
- 一份简历的项目、技能、工作经历可独立查询；
- 能够回答“某技术在哪个项目中使用”“某项目的个人职责是什么”；
- 历史数据回填失败不会影响原有 `profile_json` 和面试流程。

### 阶段 3：知识库与知识图谱重构

#### 目标

将独立 RAG 功能升级为可供出题、评分和训练复用的面试知识增强层。

#### 实施步骤

1. 扩展知识文档和 chunk 元数据：章节路径、页码、知识类型、技能标签、岗位标签、难度、版本、来源和解析方式。
2. 优化切分策略：按标题、段落、代码块、表格和语义边界切分，保留相邻 chunk 关系。
3. 建立混合检索接口：BM25/关键词、向量、图谱三类召回独立输出候选结果。
4. 实现融合和重排：先采用 RRF 或可配置加权融合，再接入 Cross-Encoder 重排，并记录每个证据的召回分和重排分。
5. 定义知识类型体系：概念、原理、实践、故障、性能、设计、面试题、反例和规范。
6. 定义知识图谱本体：实体类型、关系类型、别名、同义词和标准化规则。
7. 为三元组补充来源 chunk、原文证据、抽取模型、置信度、审核状态和版本。
8. 优先实现一跳、两跳图检索和实体消歧，不在本阶段引入 Neo4j。
9. 建立检索评测集，覆盖岗位、技术、故障、原理和项目场景；记录 Recall、MRR、NDCG、引用正确率和延迟。

#### 验收标准

- 每个被返回的知识证据均可回到原始文档、页码或 chunk；
- 检索结果能按技能、岗位、难度和知识类型过滤；
- 同一查询的混合检索效果优于当前单一检索基线；
- 图谱实体和三元组可追溯、可审核、可按来源重建；
- 不相关知识库文档不会被跨用户或跨知识库混入结果。

### 阶段 4：统一出题与动态面试能力

#### 目标

让题目生成从“技能/简历文本驱动”升级为“面试目标、结构化简历和知识证据共同驱动”。

#### 实施步骤

1. 定义 `QuestionContext` 领域对象，包含面试模式、难度、岗位、目标能力、目标技能、目标项目、简历证据、知识证据和历史表现。
2. 定义 `QuestionSpec` 输出对象，包含题干、题型、意图、难度、目标实体、参考答案、关键得分点、追问目标、所需证据和引用来源。
3. 静态规则只负责题型配额、难度边界、去重、历史覆盖和降级题库；LLM 负责主要题目语言生成。
4. 在生成题目前调用知识增强检索，并将经过重排的证据传给 LLM。
5. 对 LLM 输出执行结构化校验：题目数量、难度、证据关联、重复度、敏感内容和参考答案完整度。
6. 无简历时生成岗位/JD/技能驱动通用题；有简历时生成项目和经历验证题；项目深挖必须绑定结构化项目。
7. 将动态面试 topic 与 `target_project`、`target_skill`、知识证据和评分 rubric 关联。
8. 在动态 topic 内逐步使用 LangGraph 管理回答理解、追问策略和中断恢复；session 持久化仍由业务服务控制。

#### 验收标准

- 每道非降级题都具备题目意图、难度、评分点和可追溯证据；
- 同一用户的历史问题重复率受控；
- 有简历和无简历模式均能产生语义正确且不越界的题目；
- 项目题能明确指向候选人的项目、职责或技能证据；
- LLM 不可用时能够切换至带标签的静态题库并标记降级原因。

### 阶段 5：统一评分、报告与训练闭环

#### 目标

让评分、面试报告和训练计划共享同一套能力模型和证据链。

#### 实施步骤

1. 定义统一 `EvaluationContext`，输入包含 `QuestionSpec`、用户回答、简历证据、知识证据、历史回答和面试模式。
2. 定义统一评分输出：总分、能力维度分、得分点、缺失点、事实风险、简历一致性、评分置信度、追问建议和训练缺口。
3. 将项目真实性、个人贡献、技术深度、表达结构、系统设计和岗位匹配纳入统一能力字典。
4. 评分先执行确定性检查：回答长度、题目类型、关键字段、引用一致性和明显冲突；再调用 LLM 做语义评价。
5. 将 LLM 评分结果与规则校准结合，对低置信评分、缺少评分点和证据不足的情况明确降级标识。
6. 面试报告按能力维度、项目、技能和岗位需求汇总，不只计算平均分。
7. 训练计划按能力缺口生成任务，并关联来源题目、项目、技能、知识资料、目标分和验证标准。
8. 实现同题重练/专项重练前后对比，记录分数变化和未解决缺口。
9. 建立评分一致性和训练效果离线评测集，定期人工抽样复核。

#### 验收标准

- 每个评分结论都可定位题目、得分点和证据；
- 报告能区分答错、未回答、证据不足和评分低置信；
- 训练任务能明确说明为什么产生、练什么、如何验证完成；
- 重练结果能与原题或同能力题进行可解释比较；
- 抽样人工评分与系统评分的一致性达到预设阈值。

### 阶段 6：质量门禁、评测与产品体验完善

#### 目标

建立发布前质量保障，并把复杂能力以用户可理解的方式呈现出来。

#### 实施步骤

1. 抽象通用质量门禁，覆盖解析、OCR、切分、检索、图谱抽取、出题、评分和训练计划。
2. 每类质量门禁定义规则指标、LLM 评审条件、失败分类、重试策略和降级策略。
3. 建立单元、契约、集成、E2E 和离线评测流水线；关键指标相对基线下降时阻止发布。
4. 前端将面试上下文显式标识为通用面试、岗位面试、简历面试或项目深挖。
5. 前端展示题目来源类型、评分置信度、知识引用、解析方式和训练任务验证状态。
6. 为用户提供简历字段纠正、OCR 结果确认、知识库来源查看和训练任务反馈入口。
7. 为管理员提供任务状态、死信、成本、检索质量、模型失败率和用户反馈看板。

#### 验收标准

- 每次发布均能运行关键链路自动化测试和离线评测；
- 质量或检索指标下降能够被发现并阻止上线；
- 用户能理解题目为何生成、评分为何得出、下一步为何训练；
- 管理员能定位任务失败、模型失败、成本异常和知识源问题。

### 阶段 7：规模化与框架评估

#### 目标

根据真实业务指标决定是否需要引入更多基础设施，而不是预先堆叠框架。

#### 评估步骤

1. 基于阶段 1 至 6 的运行数据，统计任务量、P95 延迟、失败率、重试率、死信率、Token 成本、图谱规模和检索延迟。
2. 当 Redis Stream 难以支撑长流程恢复、跨服务补偿、定时调度或可视化编排时，评估 Temporal、Celery 或 Prefect。
3. 当图谱出现大规模、多跳、复杂路径或图算法性能瓶颈时，评估 Neo4j 或其他图数据库。
4. 当动态 topic 多轮策略复杂且需要可靠 checkpoint 时，扩大 LangGraph 的局部使用范围。
5. 进行小流量试点、数据双写和性能压测，再决定是否全面迁移。

#### 验收标准

- 引入每项新基础设施都有明确的性能、稳定性或维护成本收益；
- 迁移过程中业务事实源、回滚路径和数据一致性明确；
- 不因引入框架而降低现有核心面试链路的可用性。
